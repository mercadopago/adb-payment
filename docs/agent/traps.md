# Traps

Gotchas that aren't obvious from a quick read of the code, plus deliberate deviations from standard patterns.

**Confidence:** state a gotcha verifiable against the repo as a **confirmed fact** with a citation. Reserve `⚠ (to confirm by the owning team)` for genuinely tacit knowledge that can't be proven from the repo.

- Tests run **inside the Docker container**, not on the host. All `bin/run-*.sh` scripts use `docker exec magento_php ...`. Running `vendor/bin/phpunit` directly on the host fails — PHPUnit and the Magento bootstrap are only available inside the container after `make install` (verifiable in `bin/run-test.sh`).

- `make install` has two hard prerequisites that are not auto-created: `build/.env` (copy from `build/.env.sample`) and `build/credentials/auth.json` (Magento Marketplace credentials). Missing either causes an early-exit error. `make run` (start only) does not need `auth.json` but the store will not be functional (verifiable in `Makefile` lines 15–24).

- After any change to `etc/di.xml`, run `docker exec magento_php bin/magento setup:di:compile`. Without this, DI wiring changes are not picked up at runtime; Magento silently uses the old compiled class map (verifiable in `.claude/rules/module-config.md`).

- After any change to `etc/db_schema.xml`, run `bin/magento setup:db-declaration:generate-whitelist --module-name=MercadoPago_AdbPayment` to update `etc/db_schema_whitelist.json`. Omitting this breaks schema-safe column operations on upgrade (verifiable in `.claude/rules/module-config.md`).

- **Never edit an already-released Setup patch** — schema and data changes must be new `Setup/Patch/` classes so that existing merchant installs upgrade cleanly without re-running a previously applied patch (verifiable in `.claude/rules/setup-patches.md`).

- All user-facing strings must use `__('string')` **and** have matching entries in all 9 `i18n/*.csv` files (es_AR, es_MX, es_CL, es_CO, es_PE, es_UY, pt_BR, en_US, plus the base). Missing a CSV entry is not caught at compile time — it surfaces only when a merchant switches locale (verifiable in `.claude/rules/i18n.md`).

- New payment methods must be declared in **both** `etc/payment.xml` (for Magento to recognize the method) and `etc/di.xml` (for DI wiring, command pools, config providers). Declaring in only one silently skips the method in checkout (verifiable in `.claude/rules/module-config.md`).

- CSP whitelist entries in `etc/csp_whitelist.xml` must be justified — the module only adds domains it genuinely uses. Adding broad wildcards to work around Content Security Policy errors is explicitly disallowed (verifiable in `.claude/rules/module-config.md`).

- **One observer per event**, named after the event, registered in `etc/events.xml` / `etc/frontend/events.xml`. Do not overload an observer with unrelated logic (verifiable in `.claude/rules/observers.md`).

- **Interceptor plugins** in `Plugin/` must be registered in `etc/di.xml` `<plugin>` entries. Keep `before`/`after`/`around` usage minimal — `around` plugins that skip `$proceed` can silently break core Magento behavior (verifiable in `.claude/rules/plugins.md`).

- **Offline/async payment status must not be awaited inline** — reconciliation is handled by `Cron/Fetch*OrderStatus`. Stale-order cleanup is handled by `Cron/Cancel*`; do not duplicate that logic elsewhere (verifiable in `.claude/rules/cron-jobs.md`).

- Every `<message>` in `etc/mercadopago_error_mapping.xml` **must** carry a `code` attribute, and no other attribute is allowed. The `Magento_Payment` schema (`urn:magento:module:Magento_Payment:etc/error_mapping.xsd`) declares `code` as `use="required"` and defines no `message` attribute — so a node written as `<message message="...">` (no `code`) fails `setup:di:compile` with *"Element 'message': The attribute 'code' is required but missing"* and breaks the payment-error flow (e.g. the 3DS rejected challenge). The `code` is the lookup key read by `MercadoPagoVirtualErrorMessageMapper` (`etc/di.xml`, consumed by `Gateway/Command/PaymentCommand::processErrors`); the tag body holds the human-readable text, and locale translations live in `i18n/*.csv`. Never introduce a `message` attribute (verifiable in `etc/mercadopago_error_mapping.xml`, `etc/di.xml`, and the referenced XSD).

- **Error metrics must never carry raw API free-text** (`original_message`, `message`, `error`) in any field sent to Core Monitor → Datadog — that text can leak sensitive payment data (PII / CWE-532 / CWE-200). `Helper/ApiErrorCategoryMapper` resolves a **closed-set category** (`security_code`, `card_number`, `internal`, …); anything unknown maps to `internal`. **This invariant is enforced only in `Gateway/Http/Client/CreateOrderPaymentCustomClient.php` (card payments)** — the Order API clients (`Gateway/Http/Client/Order/` and `Model/MPApi/Order/`) still pass `OrderApiResponseValidator::getErrorMessage()` (raw `original_message`) and are a tracked follow-up. The card client uses `eventType = mp_api_error_{category}` (e.g. `mp_api_error_security_code`) with `value` = HTTP code and no `message` field.

- The **canonical source for the error category is `status_detail`** (exact match, mirroring `etc/mercadopago_error_mapping.xml` — e.g. `cc_rejected_bad_filled_security_code` → `security_code`). Secondary sources: `cause[].code` keyword match, then `original_message` keyword match (`fromOriginalMessage()`), then fallback `internal`. Each error path emits **exactly one** metric per operation — never one per `cause[]` item (verifiable in `Helper/ApiErrorCategoryMapper.php`).

- **Never let a metrics failure break the payment flow** — always catch and log around `MetricsClient`; keep instrumentation fail-open. Do not make metrics calls blocking on the hot path (verifiable in `Model/Metrics/MetricsClient.php`, `.claude/rules/observability.md`).

- **Per-brand CVV (`securityCode`) reconfiguration** — the MP secure `securityCode` field (`window.mp.fields.create('securityCode', {style})` in `view/frontend/web/js/view/payment/mp-sdk.js`) is created with a generic 3-or-4 length rule, so a wrong-length CVV (Visa with 4 digits, Amex with 3) passes front validation and only fails later at the payment API with `Invalid security_code_length`. It is reconfigured per brand in the `binChange` handler from `getPaymentMethods().results[0].settings[0].security_code` (`{mode, length}`). Non-obvious SDK constraints and gotchas:
    - **`settings` is update-only** (not a `fields.create()` option, per the SDK docs), so the per-brand `length` and `placeholder` are applied on the field's `ready` event via `securityCode.update({settings, placeholder})`.
    - **No `clear()`/`reset()`, and `update({settings})` does not re-validate an already-typed value** — on a brand switch a stale CVV keeps its old validity. The only way to empty a secure field is unmount + recreate: `updateSecurityCodeField()` rebuilds it via `mountSecurityCodeField()` (re-attaching `ready/error/blur/focus/validityChange`) on every `binChange`, and calls `validateFormSF.clearValidityState()` to drop the stale error + `has-error` styling that lives in the DOM outside the iframe.
    - **Double-binChange race:** the `ready` handler applies to the **captured** `field` instance and checks `window.mpCardForm.securityCode === field` — a fast rebuild can replace the global before `ready` fires, else the previous brand's settings land on the newer field.
    - **The floating label sits over the placeholder** (both at `top: 0` inside `.control-mp-iframe`). When the placeholder is inserted, `validateFormSF.markPlaceholder()` floats the label (`.in-focus`) **and** flags `_has-placeholder` — otherwise the `000`/`0000` placeholder is hidden behind the label and looks like it "isn't rendering". `removeClassesIfEmpyt` keeps `.in-focus` while `_has-placeholder` is set so a focus-then-blur without typing does not drop the label back over the placeholder.
    - **Reset per card:** `resetCardForm()` resets `cvvTooltip` to the default and calls `unmarkPlaceholder()` — otherwise the 2nd card in twocc (`finishFirstCard`/`editFirstCard`) or the cc after clearing the number inherits the previous brand's tooltip and floated label until the new bin resolves.
    - **Out-of-order guard:** the `getPaymentMethods().then` starts with `if (self.mpCardBin() !== event.bin) return;` so a stale response from an earlier bin cannot overwrite the current brand's tooltip/placeholder.
    - **i18n:** once `length` is fixed the SDK emits the single-length message, so `"securityCode should be of length '3'."` / `"…'4'."` must be registered in `iniTranslateErrorsFromSDK()` and translated in every locale CSV (the older `"…'3' or '4'."` is legacy for securityCode). The per-brand help-tooltip strings likewise need all 8 locale CSVs.
    - **Enforced at tokenization** (`createCardToken` on Place Order), not on blur — a too-short CVV shows no blur error but is blocked before reaching the payment API.
    - **CVV requiredness is driven by `security_code.mode`, not `length` (PSW-4359).** Empirically, against the real MP SDK v2 (`createCardToken` with an empty CVV): a `securityCode` field with **no settings applied is `mandatory`** (empty → `securityCode is empty`, cause `invalid_value`); `mandatory + length 0` → the SDK ignores the `0` and keeps the generic "3 or 4" (still blocks empty); **`optional + length 0` *and* `optional + length 3` both tokenize with an empty CVV**. So only `mode: 'optional'` makes the CVV optional — and `length: 0` is valid (a CVV-less brand, e.g. MLC). **Never gate applying the brand settings on `settings.length` alone**: use `settings.mode || settings.length` (in `updateSecurityCodeField()` and the `mountSecurityCodeField()` `ready` handler), skip only the placeholder/`markPlaceholder` when `length` is 0, and set `cvvRequired(settings.mode !== 'optional')` so the `*` marker (`css: {required: cvvRequired}` in `cc-form.html`/`twocc-form.html`) reflects the mode. On a failed BIN lookup, `resetSecurityCodeField()` must run (guarded by the stale-BIN check `mpCardBin() === event.bin`) so a previous brand's `optional` does not bleed onto the next, unresolved BIN. Applies to cc and twocc (shared code). ⚠ Whether MLC actually returns `length: 0` (vs `length: 3, mode: 'optional'`) for no-CVV cards is unconfirmed — check `GET /v1/payment_methods?marketplace=MLC`. Contrast: the WooCommerce plugin uses the SDK `cardForm`, which applies `mode` automatically, so it has no equivalent gap (PSW-4345).
    - **Scope:** `cc.js` and `twocc.js` both extend `mp-sdk.js` (covered); the saved-card flow (`method-renderer/vault.js`) has no `binChange` and still creates the field with the generic length (same bug class, separate fix).
    - **Residual state on invalid/cleared BIN** (`binChange`, PSW-3965) — `mpCardType` (the payload `payment_method_id`) is cleared at the top of `binChange` alongside `mpSelectedCardType`, so a previous brand does not leak into the payload at `beforePlaceOrder`. When no brand comes back (empty `getPaymentMethods().results`, or a cleared/partial BIN), `resetSecurityCodeField()` rebuilds the CVV field to drop the previous brand's placeholder/floated label; the rebuild is gated by whether a brand was applied (`hadBrand`) to avoid remounting on every keystroke of a fresh card. The empty/partial branch also sets `mpCardBin('')` so an **in-flight** `getPaymentMethods` response for the previous BIN is rejected by the stale guard instead of re-applying a brand to the just-cleared field (verifiable in `view/frontend/web/js/view/payment/mp-sdk.js`).

- **Document (CPF/CNPJ) backend check-digit validation is per-flow and MLB-only** — `Gateway/Request/DocumentIdentificationDataRequest` validates the payer document before the API as defense in depth (the frontend rule never runs when the document field is hidden). The single-card and multi-card paths must not be conflated:
    - **Single-card** (cc/pix/ticket/off) sets the non-indexed `payer_document_type`, so the builder emits `payer.identification` and validates that exact value (`getFiscalNumber`, which falls back to the billing `vatId`/`taxvat`).
    - **Multi-card (twocc)** emits **no** `payer.identification` — each card carries its own document inside its token, keyed `payer_<i>_document_identification`. The builder validates **those per-card values** (the ones tokenized) via `validateMultiCardDocuments`, *not* the billing-address fallback: the fallback can differ from what was tokenized and would risk rejecting an otherwise-valid payment. This matters because MP does **not** check-digit-validate the twocc document itself (it only enforces CVV length at tokenization), so without this an invalid CPF/CNPJ is silently accepted for twocc (verifiable in `Gateway/Request/DocumentIdentificationDataRequest.php`).
    - **The rejection metric encodes its flow in the event NAME, not a payload field** — `eventType = magento_backend_document_validation_{cc|twocc|ticket|pix}`, `value` = `CPF`/`CNPJ`/`unknown` (length-derived, never the number). The ppcore monitor proxy (`/monitor/v1/event/datadog/big/{eventType}`) only reliably indexes the event type (URL path); arbitrary top-level fields / a `tags` array are **not** guaranteed to be queryable in Datadog, so do not add dimensions there. The flow is resolved from **`getMethodInstance()->getCode()`** via `FLOW_BY_METHOD`, *not* from the document-key heuristic — cc/pix/ticket are indistinguishable by keys (all set the non-indexed `payer_document_type`). A method outside the four flows resolves to a **null flow**: still validated and rejected, just not measured (never narrow the validation to scope the metric). No `card_index`: since the proxy indexes only the event-type name, a per-card index could not be a filterable dimension without becoming another name suffix — and `validateMultiCardDocuments` does validate each card's document independently (they *can* differ), so do not document card_index as absent because "the docs are the same"; it is absent because the proxy would not make it queryable and the extra name sprawl is not justified.

- **`INVALID_USER_IDENTIFICATION_NUMBER` (API code 2067) arrives as an HTTP 400 exception, not as `status: rejected`.** The MP Payments API returns this error via `ApiException` with `original_message = "400 BAD_REQUEST \"Invalid user identification number\""`. This bypasses `GeneralResponseValidator` and `ErrorMessageMapper`/XML entirely — the `mercadopago_error_mapping.xml` entry is a defensive fallback only. The fix lives in `CreateOrderPaymentCustomClient` `catch (\Throwable $e)`: `$originalMessage` is extracted before the 3DS guard and checked via `stripos($originalMessage, self::INVALID_IDENTIFICATION_SDK_MESSAGE)` (the SDK literal is centralised in that `public const` so a string change breaks the test immediately). The metric category in the HTTP-400 path resolves via `CAUSE_KEYWORD_MAP['identification']` (pre-existing keyword match); the new `STATUS_DETAIL_MAP` entry covers only the defensive `fromResponse()` path (PSW-3989).

- **`bin_not_found` (cause code 10105) surfaces two different messages depending on the layer.** The **frontend** shows an inline card-number field error *"The card number entered was not recognized. Please check and try again."* when the MP SDK `getPaymentMethods` returns no `results` in `binChange` (`view/frontend/web/js/view/payment/mp-sdk.js`). The **backend** maps `bin_not_found` → *"One or more of the card details were entered incorrectly..."* via `etc/mercadopago_error_mapping.xml` (the core `errorMessageMapper`, **path A**: a `rejected` response with `cause` → `GeneralResponseValidator` → `PaymentCommand::processErrors`). Only path A is handled: if the API returns `bin_not_found` as an **HTTP 400**, the SDK throws and the message goes out via `__($e->getMessage())` in the `CreateOrderPaymentCustomClient` catch, **bypassing the mapper** (path B, not handled — see PSW-3821). Do not "unify" the two messages assuming a single source of truth. The frontend message's shown/cleared state is **not** driven only by `binChange` (which fires only when the first 8 digits change): it is persisted in a `binUnrecognized` flag and **re-rendered by the card-number `validityChange` handler** (precedence: SDK format error → `binUnrecognized` message → valid). Without this, a length-only edit that does not change the BIN (e.g. deleting a 20th digit back to a valid length) would clear the message and mark the field valid even though the BIN is still unrecognized.

- **Pre-submit validation is a single ordered gate in `beforePlaceOrder`** (`cc.js`, `twocc.js`, PSW-3968). The three checks run in order and short-circuit on the first failure: `$(formElement).valid()` (jQuery) → `installmentsAreValid()` → `cardNumberIsValid()` (Luhn+length). Each maps to a code fed to `showError()` in `mp-sdk.js`. Non-obvious points: (1) `invalid_form` is **intentionally silent** in `showError()` — jQuery `.valid()` already renders inline field errors, so adding a global banner would double-message; only `invalid_installments` and `invalid_card_number` add a `messageList` banner. (2) `installmentsAreValid()` returns **true** when `installmentWasCalculated()` is false — parcels are only required once the select is rendered for a resolved BIN, so pix/boleto (which never calculate) and a not-yet-resolved card are not blocked here; the real block is when the select is shown but `mpCardInstallment()` is still null. Before PSW-3968 this case failed **silently** at `generateToken`'s internal `if (!selectedPayerCost) return false;` with no user feedback. (3) The `cardNumberIsValid()` guard **inside** `generateToken()` stays as defense in depth — redundant with the gate but retained; the only callers of `generateToken()` are `cc.js` and `twocc.js`. `vault.js` has its own `beforePlaceOrder` and never calls `generateToken()` (saved card → CVV only, no cardNumber field). (4) `twocc.js` keeps its two-card specifics after the shared gate: `progressHasError()` + `#input-progress` focus, `cardIndex()`, and `finishFirstCard()`. (5) `generateToken()`'s argument is vestigial — it reads `cardIndex()` internally. Scope: `vault.js` (saved card) is **not** unified — follow-up (verifiable in `view/frontend/web/js/view/payment/method-renderer/cc.js`, `twocc.js`, `mp-sdk.js`).

- **Luhn (card-number checksum) is OFF by default in the MP Secure Fields; it is enabled per-field via `enableLuhnValidation: true`** in `window.mp.fields.create('cardNumber', {style, enableLuhnValidation: true})` (`view/frontend/web/js/view/payment/mp-sdk.js`, PSW-3966). Without the flag the `validityChange` callback validates only length/type/empty — a number with a recognized BIN and correct length but a wrong check digit emits `errorMessages: []` (looks valid) and is only rejected later by the API at `createCardToken` (proven empirically via an e2e probe: default → `[]`; flag on → error). With the flag on, Luhn arrives in `validityChange` as `{cause: 'invalid_value', message: 'card number rejected on Luhn Validation', details: {reason: 'luhn'}}`; the raw English message is swapped for the translatable `invalidCardMsg` before display, and `details.reason === 'luhn'` disambiguates it from the CVV's own `invalid_value`. Requires MP SDK ≥ 2.74.0 (added 2026-07-29; the prod CDN `sdk.mercadopago.com/js/v2` serves ≥ 2.74.2) — the `cardForm` used by the WooCommerce plugin is a separate, later-supported path (PSW-4338), do not assume the two plugins share the same Luhn readiness. **A single `cardNumberIsValid` flag backs the field** (true when the SDK reports no error at all — length + Luhn); it feeds both the `generateToken` submit gate and the recognized-BIN clear in `binChange`. That branch clears the field only when `cardNumberIsValid()` is true (not length-only), otherwise a late `getPaymentMethods` response could wipe a Luhn error that `validityChange` had just rendered. Scope: `cc.js` and `twocc.js` both extend `mp-sdk.js` (covered); `vault.js` creates no cardNumber field (saved card → CVV only).

- **E2E CVV fill must wait for the securityCode iframe remount cycle, not for installments.** When a recognized BIN is entered, `mp-sdk.js` fires `binChange` which calls `updateSecurityCodeField()` → `securityCode.unmount()` + `mountSecurityCodeField()`. During unmount the iframe is removed from the DOM (detached); after remount a new iframe appears. `getInstallments()` and `getPaymentMethods()` are started in parallel (lines 216-217 of `mp-sdk.js`); only `getPaymentMethods()` triggers the remount. In tests, the reliable sequence is: (1) fill card number, expiry, cardholder; (2) wait for `iframe[name="securityCode"]` to be `'detached'` (unmount signal, `.catch(()=>{})` for unrecognized BINs); (3) wait for the frame-locator CVV input to be `'visible'` (remount complete); (4) fill CVV; (5) wait separately for the installments selector if needed. A fixed `waitForTimeout` or using the installments selector as a proxy for CVV readiness is insufficient: a slow `getPaymentMethods()` response will remount the iframe after the timeout/installments signal, clearing the already-filled value. Applies to all one-card and two-card E2E flows that use the MP SDK Secure Fields (verifiable in `e2e/flows/checkoutcustom/`, `e2e/tests/checkoutcustom/`).

- **Magento's JS phrase extractor only picks up strings inside `$t(...)` at the call site.** A literal passed as data to a helper that applies `$t()` internally (e.g. `validateFormSF.toogleValidityState`) is **not** extracted into `js-translation.json`, so it renders untranslated even with the CSV entries present. Wrap the literal in `$t()` where it is written (the helper's own `$t` is then a no-op on the already-translated string). `js-translation.json` is regenerated by `setup:static-content:deploy`; in `default`/`developer` mode it may need a manual regen for a new string to appear translated.

- ⚠ Webhook notification endpoints (`/mp/notification/*`) receive POST callbacks from the MercadoPago platform. The merchant must configure the notification URL in the MP merchant dashboard to point to their store's domain. Without this configuration, async payment reconciliation falls back entirely to cron polling. *(to confirm by the owning team)*

- ⚠ `mp-plugins/php-sdk` timeout and retry behavior is not configured in this module — it uses the SDK's defaults. If a merchant experiences MP API timeouts, there is no in-module tuning point; changes would need to go into the SDK or be wrapped at the `Gateway/Http/` layer. *(to confirm by the owning team)*

- This is a **Magento module, not a Fury web service** — do not add a standalone HTTP server, Fury scopes, or a `.fury` deploy surface to this repo.

- **Do not alter the `mp-plugins/php-sdk` contract expectations** without checking the SDK version pinned in `composer.json` (`^3.6.1`). Any interface change to the SDK must be coordinated with the SDK version constraint (verifiable in `composer.json`).

- **In the payment authorization / capture / refund flow, never call the MercadoPago SDK/API directly from request builders, response handlers, or `Model/…/Payment` classes** — outbound calls go through `Gateway/Http/Client/` (idempotency + error mapping). **Known exceptions — do NOT "fix" these into the gateway:** read/query and admin/vault/console flows legitimately instantiate the SDK `HttpClient` directly outside `Gateway/Http/`: `Model/MPApi/*` (`PaymentGet`, `Order/OrderGet`, `Order/OrderNotificationGet`), `Model/Api/CreateVaultManagement`, `Model/Adminhtml/Source/MerchantPaymentMethods`, and `Model/Console/Command/Adminstrative/*` (verifiable in `.claude/rules/payment-gateway.md`).

- **Never build a payment request without the idempotency key** — the idempotency-key helper (`Helper/`) must be included in every outbound MP API request. Missing it risks double charges on retry (verifiable in `Gateway/Request/` builders and `Helper/`).

- **Do not hand-instantiate request builders** — they are composed via `BuilderComposite` in `etc/di.xml`. Wire new builders through DI; hand-instantiating them bypasses the composite and silently omits the other builders in the chain (verifiable in `etc/di.xml`).

## Deliberate deviations from standard/team patterns

- **Hand-written mocks in `Tests/Unit/Mocks/`** — these are deliberate hand-authored mocks, not generated output. They look like generated code but are maintained manually. Do not treat them as safe-to-regenerate or low-signal (verifiable: no `@generated` or `DO NOT EDIT` header in the files).

- **`Console/Command/Adminstrative/` has a typo** — the directory is named `Adminstrative` (missing an 'i'), not `Administrative`. This is the established path; renaming it would break the PSR-4 autoloading without a corresponding `composer.json` update (verifiable in `Console/Command/Adminstrative/`).

- **Multi-version CI matrix (2.4.4–2.4.7)** — the module deliberately maintains compatibility across four Magento LTS versions. Code changes must not use APIs or syntax available only in newer Magento or PHP versions without conditional guards (verifiable in `.github/workflows/test-m2.4.*.yml`).
